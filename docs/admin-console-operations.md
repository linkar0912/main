# Linkar owner console operations

The owner console is served only from `https://admin.linkar.in/admin`. Access is granted by exact Supabase Auth UUIDs in `PLATFORM_OWNER_USER_IDS`; email addresses are never authorization inputs. Sign in on the admin host, enroll a TOTP factor under **Security**, and reach AAL2 before opening operational pages. When the app and admin hosts share an eligible parent domain, Supabase cookies use that domain to support the login handoff. Admin access still requires the exact owner UUID and AAL2 on each protected request.

Use **System** for bounded web, PostgreSQL, Valkey, worker, queue, configuration-presence, throughput, and reconciliation status. Queue pause/resume and reconciliation commands require an operator reason and are written to the immutable audit trail. A paused queue stops new work from being claimed; resume it after the incident. When a queue card shows failed jobs, **Review failed jobs** lists the 50 most recent failures for that queue with their job name, safe failure code, attempt count, and failure time. Select the jobs to retry (at most 100 per command) and choose **Retry selected**; the retry needs an operator reason, is audited, and is rejected if any selected job is no longer in the failed state. The UI never exposes URLs, credentials, tokens, payloads, or stack traces.

The worker process consumes two BullMQ queues: `webhooks` for realtime events and interactive follow-ups, and `bulk` for broadcasts and lead delivery. Its health endpoint is healthy only while both consumers are running and connected to Redis. During the first rollout, the realtime consumer also finishes bulk jobs that were already waiting in the old queue. The System queue cards show both queues; waiting includes prioritized jobs.
During rollout, prefer bringing up the replacement singleton worker before the web service. If the image deploy updates both together, newly enqueued bulk jobs remain durable until the new consumer starts. Verify the worker health endpoint and both queue cards after deployment; the replacement worker can drain jobs from either queue.

Use **Audit** to filter privileged events and export the fixed safe CSV projection. Export itself requires a reason and is audited. CSV cells that could be interpreted as spreadsheet formulas are neutralized. Commands that change a plan, an entitlement, a workspace, a user's email or access, or a membership record the previous state in the audit row's `before` field.

On a workspace page, **Workspace export** needs its own reason, is audited with row counts, and refuses workspaces above 50,000 rows. **Pause active automations** records which automations it stopped; **Resume previously paused** re-activates exactly those, skipping any edited since. On a user page, **Suspend/Restore Linkar access** and **Ban/Unban Auth login** are separate controls: unbanning never lifts a Linkar suspension, and Linkar access cannot be restored while the Auth ban is in force. User search reads at most the first 5,000 Supabase Auth identities plus matching workspace members, and says so when it stops early.

Production must set `APP_URL=https://app.linkar.in`, `NEXT_PUBLIC_APP_URL=https://app.linkar.in`, `ADMIN_URL=https://admin.linkar.in`, and `PUBLIC_SITE_URL=https://linkar.in`. OAuth callbacks belong to `app.linkar.in`; marketing and legal pages remain canonical on `linkar.in`. DNS, deployments, database administration, and secret rotation remain in Cloudflare, Dokploy, and Supabase, not inside Linkar.

Billing is ready only when the web deployment contains all nine Razorpay variables (`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, and the six monthly/annual plan IDs), `APP_URL` is the canonical app origin, and `WORKER_HEALTH_URL` points to the worker heartbeat endpoint. Store every value directly in Dokploy; never paste values into logs, commits, tickets, or audit reasons. Configure Razorpay to send subscription events to `https://app.linkar.in/api/razorpay/webhook`, deploy both web and worker after changing environment values, and run `pnpm preflight:billing` inside the configured release. The preflight reports missing variable names and safe plan IDs, but never prints secrets.

For an incident: pause the affected queue, record the incident reason, inspect safe failure codes and worker health, fix the external cause, run the relevant reconciliation, open **Review failed jobs** on the affected queue and retry only the selected failures whose cause is fixed, then resume. Rotate provider/Supabase secrets in deployment storage and redeploy both web and worker; never paste secrets into the audit reason.

## Owner MCP (Claude)

The owner console is also an MCP server at `https://admin.linkar.in/api/admin/mcp`, so Claude can run any console action for you: users, workspaces, plans and limits, invite codes, integrations, operations (automations, sequences, broadcasts, contacts, tracked links, deliveries, webhooks), deletions, queues and reconciliation, the audit log and Meta data deletion requests. Each tool calls the same route handler the console uses, so the same validation, version checks, owner-workspace protection, confirmation challenges and audit rows apply.

**Create a key.** Open **Security** at AAL2, choose **Create key** under **Claude MCP keys**, and pick a name, the access (**Read only** or **Read and write**) and an expiry (1, 7, 30 or 90 days). The key (`lkadm_…`) is shown once with the command to connect Claude Code:

```bash
claude mcp add --transport http --scope user linkar-admin https://admin.linkar.in/api/admin/mcp --header "Authorization: Bearer lkadm_…"
```

The command puts the key in your shell history too; prefix it with a space (with `HISTCONTROL=ignorespace`) or clear that history line. Claude Code stores the header in your user configuration (`~/.claude.json`). Treat that file like a password store, and revoke the key if the machine is lost. Claude Desktop and claude.ai connectors need OAuth, which this endpoint does not offer; use Claude Code.

**What a key can do.** A read-only key sees only the read tools, and the server refuses its writes (`mcp_key_read_only`). A read-and-write key can do everything the console can, including permanent deletion. Write tools need a `reason`, which goes into the audit row. Two-step actions (deletion, synthetic cleanup, integration disconnect) still return a confirmation phrase and a single-use challenge first. Claude is told to show you the impact and wait for your go-ahead before the second step. Audit rows made with a key are labelled **via Claude MCP key**. On the **Audit** page, set **Made with** to **Claude MCP key** to see them all. **This key’s actions** on a row, or **Audit log** next to a key on **Security**, shows everything one key did; use it after revoking a lost key. (In the database those rows have origin `mcp` and session `mcp_key:<key id>`.) Reads are not audited (as in the console), but every tool call is logged with the key id and tool name.

**What a key cannot do.** Keys cannot mint or revoke keys, or enroll or remove MFA factors. Those stay in the browser at AAL2. DNS, deployments, database administration and secret rotation remain outside Linkar, as above.

**When a key stops working.** Once a key stops working, Claude Code reports the server as failing to authenticate (401); create a new key and run the `claude mcp add` command again, after `claude mcp remove linkar-admin --scope user`. A key stops working at once, on its next request, when it is revoked or expires, when its owner leaves `PLATFORM_OWNER_USER_IDS`, when the owner's platform access is suspended, or when the owner's sessions are revoked (password reset or "sign out everywhere": keys created before that moment die with the sessions). Each owner can hold 10 active keys. Ten failed key attempts from one network within 15 minutes are answered with 429 for the rest of the window. The endpoint answers JSON only (no event stream) and refuses browser requests from other origins.

The `AdminMcpKey` table is created by the `20261025120000_admin_mcp_keys` migration and stores only the SHA-256 of each key. Deploy the migration before the web image that serves the endpoint.
